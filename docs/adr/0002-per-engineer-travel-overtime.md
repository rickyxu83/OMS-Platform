# ADR 0002: 工单加班的路上时间按工程师各自申报

## 状态

草案

## 背景

同一张服务工单可以有多名工程师协作（主责工程师 `service_orders.assigned_engineer_id` 加上 `service_order_engineers` 里的协作工程师）。工单加班申请对这些工程师都开放，各自提交各自的申请（按 `submitted_by` 区分）。

但工单的出勤时间只有一份：`service_reports` 对每个工单唯一一条（`uk_service_reports_order_id`），存一组四个时间戳——出发（`departure_at`）、到达/开工（`actual_start_at`）、完工（`actual_end_at`）、返回（`return_at`）。`overtimeSegments()` 把这四个时间拆成去程、工作、回程三段。

现实场景：苏州工程师和上海工程师去同一地点加班，往返的出发、返回时间天然不同，却共用同一张工单。当前模型下两人只能按同一组工单时间申请，对至少一方是错的。

值得注意的矛盾：工作**内容**已经按工程师区分（`service_report_work_entries` 以 `(service_order_id, engineer_id)` 为键），但出勤**时间**仍是每个工单一份。

## 决策

工单加班申请时，允许工程师**手动填写去程和回程的时间**，默认带出工单时间；工单侧数据不改。

已确认范围：

- **时间只落在申请上**：手动改过的去程出发、回程返回时间只影响本人这条 `attendance_requests` 记录，`service_reports` 的时间永不改动，仍是全工单共享的一组值。
- **工作段锁死**：三段中只放开去程、回程可手动填。工作段（到达→完工）严格按工单时间，不可改。到达、完工两个锚点也始终来自工单。
- **所有工程师都能改**：不区分主责/协作。主责工程师若无差异直接用默认值提交即可，零负担。
- **最小校验，只防倒挂**：去程出发 ≤ 工单到达；回程返回 ≥ 工单完工；出发/返回本身为合法时间。不设“必须与工单差多少”“单段路上时长上限”等业务上限。有效时长仍由现有 `overtimeWindow`（掐平日 18:00、整点取整）判定，算不出有效时长则不产生加班。
- **路上时间统一走合并**：去程/回程分开填时间，但申请加班时长仍按原 `combineTravelSegments` 逻辑合并成一条“来回路上实际时间”申请（`source_detail = 'travel'`）。取消单独申请去程或回程的能力，`travel_out` / `travel_back` 两个 segment 键从产生、校验、去重整体退役。
- **留痕给审批人**：工程师填的原始去程出发、回程返回时间存进申请的 `source_snapshot` JSON，审批人能对照“申请人自报往返 vs 工单时间”。申请上 `start_at`/`end_at` 仍是 `overtimeWindow` 掐算后的合并结果。
- **去重收敛**：一个工单、一个工程师，路上时间只有一条 `travel` 申请。占用检查只判断该工程师对该工单是否已有未作废的 `travel` 申请。历史遗留的 `travel_out`/`travel_back` 申请仍按 `travel` 占用对待，避免老数据被重复申请。

## 理由

- 用户明确倾向轻量方案：不新增按工程师的时间表，改动只落在申请侧，工单结构零变更，回滚成本低。
- 通勤时间天然因人而异（不同出发城市），而现场工作时间对同一工单的多名工程师应当一致，锁死工作段可防乱填，也保住付薪段（`pay`，可能 2x/3x）按工单事实结算的稳妥性——去程/回程按既有规则只能转调休。
- 统一走合并、退役单程键，消除了 `travel` 与 `travel_out`/`travel_back` 三键互斥这套绕人的去重逻辑，模型更简单。

## 后果

- `attendance_requests` 不新增列，扩展点落在既有 `source_snapshot` JSON（新增原始往返时间字段）。
- `overtimeSegments`、`combineTravelSegments`、`usedOvertimeSegments`、工单加班申请入口的校验与去重都要相应调整，`travel_out`/`travel_back` 退役。
- 前端工单加班表单需新增去程出发、回程返回两个可编辑时间输入，默认带工单值。
- 管理端有可见改动，版本号需随实现同步提升。

## 修订记录

### 2026-08-27：路上时间从「合并一条」反转为「去程/回程两条独立申请」，多段审批操作由审批列表成组解决

产品复核后推翻本 ADR 中「路上时间统一走合并」一节：合并显示（如去程 11:10 出发、回程 20:35 到家，合并为 11:10–20:35 共 6.5h）把中间工作时间也包进起止区间，审批人看不清每程真实时段与时长。

变更要点：

- **拆回两条独立申请**：`travel_out`（去程路上：出发→工单到达）与 `travel_back`（回程路上：工单完工→返回）各自过 `overtimeWindow` 掐算、各自生成一条 `attendance_requests`（`source_detail` 区分），取代原合并的 `travel` 一条。`travel_out`/`travel_back` 两个 segment 键**重新启用**，本 ADR 的「退役」结论作废。
- **去重反转**：一个工单、一个工程师，每种时段（travel_out / travel_back / work）只允许一条未作废申请；**历史合并的 `travel` 记录对去程、回程两段均有占用**，避免老数据被重复申请（与本 ADR 原「历史 travel_out/travel_back 按 travel 占用」方向相反）。
- **入参兼容**：旧客户端按 `segmentKey: 'travel'` 申请时自动展开为去程+回程两段，接口不破坏。
- **留痕按段**：`travel_out` 快照记 `reportedDepartureAt`，`travel_back` 记 `reportedReturnAt`；无有效加班时长的程不生成（如平日去程整段在 18:00 前），只生成另一程。
- **审批操作合并靠 UI 成组**：同一工单的多段申请（去程+工作+回程）在审批列表合并为一组展示，组头一组「全部通过/全部驳回」按钮批量审批（驳回一次填原因应用于全组）——解决「同一工单审批人要点多次通过」的痛点，但不改申请数据模型。
- 列表显示按 `source_detail` 细分「去程路上/回程路上」；历史合并数据显示「来回路上实际」不受影响。
