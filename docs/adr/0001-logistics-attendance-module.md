# ADR 0001: 后勤考勤模块纳入当前 OMS

## 状态

草案

## 背景

计划增加后勤相关能力：

- 请假：特休、病假、事假、婚假、丧假
- 特休：每月汇总，台籍和陆籍规则不同
- 加班
- 换休

当前 OMS 已经具备管理端、账号、角色、权限、审计、系统设置、工单和工时报表等横向能力。新模块会依赖这些能力，尤其是用户身份、审批权限、审计记录和月度汇总。

## 决策

后勤考勤模块应直接做在当前项目里，但必须作为独立业务边界实现，不混入现有工单模块。

已确认范围：

- 覆盖所有员工。
- 员工自己提交申请。
- 请假、加班、换休都不要求先申请后执行，允许事后补单。
- 审批流为：员工提交 -> 主管审批 -> 行政审批。
- 主管审批人来自员工档案中指定的直属主管。
- 行政审批由拥有 `attendance.admin.approve` 权限的人员处理。
- 申请在行政终审前允许申请人撤回；行政终审通过后允许行政作废。
- 台籍、陆籍特休规则先预留规则分支，具体计算规则后续补充。
- 加班申请有两种处理结果：转换休或转加班费。
- 换休申请消耗换休总余额，不绑定具体加班来源。
- 月度汇总先作为报表，不做月结锁定。

建议边界：

- 后端新增独立模块，例如 `backend/src/modules/attendance-leave`
- 前端新增独立管理端页面组，例如“后勤考勤”
- 权限新增独立 permission key，例如 `leave.view`、`leave.apply`、`leave.approve`、`overtime.view`、`overtime.approve`
- 数据表独立建模，不复用 service orders 或 timesheet 表表达请假、加班、换休
- 可读取现有 users 作为员工目录，但员工属性需要补充独立档案，例如籍别、入职日、假别规则归属

## 理由

- 这个模块需要统一登录、权限、审计和人员主数据，当前项目已经具备这些基础能力。
- 请假、特休、加班、换休之间存在审批、余额和报表关系，拆成另一个系统会增加账号、权限和数据同步成本。
- 现有项目已有月报和工时概念，但后勤考勤的规则、审批和余额不同，直接复用工单或工时报表会污染模型。

## 后果

- 当前 OMS 会从服务工单系统扩展成更完整的内部运营系统。
- 需要设计员工档案、假别规则、审批流、余额流水、月度报表等新模型。
- 管理端版本号在实现可见页面时必须同步提升。
- 需要明确哪些角色能作为主管审批、哪些角色能行政审批、哪些角色能查看全员和维护规则。

## 后续待确认

- 台籍、陆籍特休规则的精确定义和生效日期。
- 病假、事假、婚假、丧假是否只记录，还是也要余额和薪资扣款口径。
- 加班费结果是否需要导出给薪资系统或财务。
