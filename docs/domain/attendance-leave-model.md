# 考勤管理领域模型草案

## 目标

在 OMS 内增加独立的考勤管理模块，覆盖所有员工的请假、特休、加班、换休和月度报表。模块复用现有账号、权限、审计和管理端，但业务数据独立建模。

## 申请类型

一期建议拆成三类申请，而不是只做一个大表单：

- 请假申请：特休、病假、事假、婚假、丧假
- 加班申请：记录加班原因、时间、类型和处理结果
- 换休申请：消耗换休总余额

拆分原因：

- 请假主要消耗假别余额或形成请假记录。
- 加班可能产生换休余额，也可能进入加班费报表。
- 换休只消耗换休余额，不需要绑定具体加班来源。

时间计量：

- 底层统一按小时存储。
- 前端表单提供半天、一天等快捷选项。
- 月度报表可以按小时展示，也可以按标准工时换算成天。

提交规则：

- 请假、加班、换休都不要求先申请后执行，允许事后补单。
- 申请记录需要同时保存业务发生时间和提交时间。

## 审批流

已确认审批顺序：

1. 员工提交
2. 主管审批
3. 行政审批

已确认审批人来源：

- 主管审批人来自员工档案中指定的直属主管。
- 行政审批人来自权限控制，拥有 `attendance.admin.approve` 权限即可处理行政终审。

建议状态：

- `draft`：草稿
- `pending_supervisor`：待主管审批
- `pending_admin`：待行政审批
- `approved`：已通过
- `rejected`：已驳回
- `withdrawn`：已撤回
- `voided`：已作废

撤回和作废规则：

- `pending_supervisor` 和 `pending_admin` 状态下，申请人可以撤回。
- `approved` 状态下，拥有 `attendance.admin.approve` 权限的行政审批人可以作废。
- 撤回需要释放申请占用的余额。
- 作废需要生成反向余额流水，冲回已入账或已扣减的特休、换休余额。

待确认：

- 作废是否需要上传附件。

## 员工档案

现有 `users` 是登录账号，不应承载所有考勤规则。建议新增员工档案表，与 `users.id` 可选关联。

核心字段：

- 员工姓名
- 关联用户 ID
- 籍别：台籍、陆籍
- 入职日期
- 离职日期
- 直属主管员工 ID
- 是否启用考勤
- 特休规则组

上线前需要为所有启用考勤的员工补齐直属主管。没有直属主管的员工不能提交需要主管审批的申请，除非后续增加跳过主管或指定替代审批人的规则。

## 余额模型

不要只存当前余额。建议采用“余额账户 + 余额流水”。

账户类型：

- 特休余额
- 换休余额

加班申请不是一个可消耗余额账户，而是产生两类结果：

- 路上往返实际时间只能增加换休余额。
- 实际工作时间选择换休时增加换休余额。
- 实际工作时间选择加班费时不增加换休余额，进入加班费报表口径。
- 换休申请消耗换休总余额，不绑定具体加班来源。

流水动作：

- 发放
- 申请占用
- 审批通过扣减或入账
- 驳回释放
- 撤回释放
- 手工调整

## 月度报表

已确认月度汇总先做报表，不做月结锁定。

报表建议维度：

- 员工
- 月份
- 请假小时数，按假别拆分；需要时按标准工时换算成天
- 特休期初、发放、使用、调整、期末
- 加班申请总时数
- 转换休时数
- 转加班费时数
- 换休使用时数
- 换休期末余额

## 一期切法

建议一期先做最小闭环：

1. 员工档案：补齐籍别、入职日、主管。
2. 请假申请：支持五种假别，走主管和行政两级审批。
3. 加班申请：支持路上时间、实际工作时间，支持转加班费或转换休。
4. 换休申请：消耗换休总余额。
5. 月度报表：按员工和月份汇总，不锁月。

暂缓：

- 台籍、陆籍特休自动计算细则。
- 薪资系统对接。
- 月结锁定。
- 复杂班别和法定节假日日历。
