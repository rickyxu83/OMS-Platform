# 审批全程展示加班工单

## Goal

让加班申请所关联的服务工单在整个审批链路中持续可见，使直属主管、上级主管、人事/行政及最终审批人能根据实际工单内容判断加班是否合理。

## Confirmed Facts

- 加班申请只能从服务工单选择并提交，申请记录通过 `source_type = 'service_order'`、`source_id` 和 `source_detail` 保存工单及加班时段关联，见 `backend/src/modules/attendance/controller.js:560`。
- 加班申请表单已经展示工单号、客户、设备、服务类型、联系人、服务时间节点和问题描述，见 `frontend-admin/src/pages/Attendance.tsx:919` 与 `frontend-admin/src/pages/Attendance.tsx:1125`。
- 审批人、申请人和全员记录都复用 `RequestList`；当前该组件只展示加班类型、结果、时间、小时数和审批轨迹，没有展示关联工单，见 `frontend-admin/src/pages/Attendance.tsx:1846`。
- `/attendance/requests` 当前查询考勤记录、人员、附件和审批步骤，但没有补充服务工单内容，见 `backend/src/modules/attendance/controller.js:1304`。
- 多级审批状态均使用同一批申请列表数据，因此只要统一补全申请响应并在 `RequestList` 渲染，各级审批即可保持一致展示。

## Requirements

- 关联服务工单的加班申请必须在“待我审批”中展示可用于判断加班合理性的工单摘要。
- 同一工单摘要必须随申请进入直属主管、后续主管、人事/行政及最终审批阶段，不因审批状态变化而消失。
- “我的申请”和“全员申请记录”也应使用同一展示逻辑，避免同一申请在不同列表中信息不一致。
- 非工单加班记录、请假和调休记录不得出现空白工单卡片或错误字段。
- 工单信息缺失或关联记录不可用时，审批列表仍须正常加载，并至少保留工单编号或关联 ID 的降级提示。
- 展示不得依赖审批人另有“查看工单”权限或额外跳转，审批所需摘要应直接随考勤申请接口返回。
- 审批列表默认展示工单摘要，并提供行内展开详情；摘要包含工单号、客户、设备、服务类型和问题描述，展开后补充联系人及出发、到达、完成、返回等时间节点。
- 新提交的工单加班申请必须保存申请提交时的工单摘要快照；后续审批优先展示该快照，避免工单修改导致不同审批人看到不同内容。
- 既有历史申请没有快照时，接口应回退读取当前关联工单；当前工单也不可用时，使用申请记录中的工单 ID 和加班时段提供降级提示。

## Acceptance Criteria

- [ ] 工程师提交工单加班后，直属主管的“待我审批”能直接看到关联工单摘要。
- [ ] 直属主管批准后，下一审批人看到的工单摘要与前一步一致。
- [ ] 人事/行政及最终审批阶段能看到同一工单摘要后再执行通过或驳回。
- [ ] 提交申请后修改原工单，不会改变该申请在后续审批步骤中展示的工单摘要。
- [ ] 历史无快照申请仍能从当前工单读取摘要；工单不可用时列表不报错并显示降级信息。
- [ ] 工单摘要直接显示工单号、客户、设备、服务类型和问题内容，并可展开查看联系人及完整服务时间节点。
- [ ] “我的申请”和“全员申请记录”中的工单加班也展示相同摘要。
- [ ] 普通请假、调休及无有效工单详情的历史记录仍能正常显示。
- [ ] 后端测试覆盖工单摘要随 `/attendance/requests` 返回及无关联工单时的降级行为。
- [ ] 管理端 `npx tsc --noEmit` 与 `npm run build` 通过，后端 `npm run check` 通过。
- [ ] 这是管理端可见功能变更，`frontend-admin/package.json`、`frontend-admin/package-lock.json` 顶层版本和 `frontend-admin/src/config/app.ts` 的 `APP_VERSION` fallback 三处版本一致提升。

## Out of Scope

- 不改动现有审批层级、审批权限或状态流转规则。
- 不重做工单详情页，也不要求审批人跳转到完整工单页面。
- 不回填所有历史申请的不可变快照；历史申请仅在读取时回退关联当前工单。
- 不复制完整工单、附件或服务报告正文，只保存审批所需摘要字段。

## Technical Notes

- 采用 `attendance_requests.source_snapshot JSON NULL` 保存申请提交时的工单摘要，沿用项目现有 JSON 字段及 `ensureSchema()` 惰性迁移模式。
- 新申请写入快照；读取申请列表时优先解析快照，历史无快照记录再批量查询当前关联工单，避免逐条查询。
- 不采用独立快照表：当前只有工单加班来源需要该能力，单列 JSON 的边界更小。
- 不采用纯实时关联：无法保证各级审批看到一致内容。
- 前端复用 `RequestList`，使用项目已有的原生 `<details>` 展开模式；不新增工单页面跳转，也不要求审批人拥有额外的工单查看权限。
